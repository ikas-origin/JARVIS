# JARVIS 1.1：终端体验与可靠性增强

## 本版目标

1.1 不扩张为通用个人助理，而是同时改善两件事：让 Coding Agent 的运行轨迹更容易阅读；让关键控制逻辑比 1.0 更可验证。

## 用户体验改进

- 交互启动页加入钢铁侠风格字符画。
- 状态栏集中展示版本、workspace、模型、Git 分支、session、ReAct/Spec 模式、工具数、stream 和审批策略。
- `YOU`、`JARVIS`、`TOOL`、`VERIFY`、`CONTEXT` 使用独立标签，不再把回复、工具日志和用户输入挤在一起。
- 工具事件不再打印完整写入内容；`content`、`old_text`、`new_text` 只显示字符数。
- 成功文件工具显示路径/数量等元数据；成功命令显示退出码和最后一行结果。
- 最终状态压缩为一行，展示 stop reason、turns、tools、tokens、verification 和耗时。
- ANSI 只在 TTY 中自动启用；支持 `--no-color`、`NO_COLOR` 和 `JARVIS_NO_COLOR`，JSON 输出不受影响。

界面逻辑独立在 `terminal_ui.py`，不进入 Agent loop，因此终端样式不会改变 JSON 自动化接口或模型行为。

## 核心逻辑改进

### 1. 探查命令与验证命令分离

`run_command` 现在必须声明：

```json
{"command": "python -m unittest", "purpose": "verify"}
```

`purpose="inspect"` 用于查看版本、目录、Git diff 等信息；`purpose="verify"` 只用于测试、构建、lint、类型或语法检查。普通文件写入后，只有 `verify` 命令返回 0 才能解除验证门。成功的 `inspect` 命令不能让 Agent 宣布完成。

这解决了 1.0 中“任意返回 0 的探查命令都可能被当成验证”的问题，并在轨迹中记录模型的命令意图。

边界：`purpose` 仍由模型选择，JARVIS 不能从字符串上证明该命令覆盖全部需求。后续 Spec 可以把验收命令和需求 ID 存为结构化记录，并由程序执行预先批准的命令，而不是只相信标签。

### 2. 递归工具参数校验

1.0 只校验顶层 required、extra 和基本类型。1.1 在 `ToolRegistry` 中递归支持：

- object properties、required、additionalProperties；
- array item 类型与 minItems/maxItems；
- enum；
- string minLength/maxLength；
- number/integer minimum/maximum；
- 防止 Python `bool` 被误当成 number/integer。

因此 `read_files(paths=[123])` 会在 handler 前以稳定 `tool_error` 拒绝，非法命令 purpose 和超界 timeout 同理。它仍是项目需要的 JSON Schema 子集，不声称实现完整标准。

### 3. 更严格的流式协议解析

SSE 解析新增以下拒绝条件：

- 非 UTF-8 事件；
- 非法 JSON 或非 object 根；
- choices 不是 array；
- choice/delta/tool call/function 不是 object；
- tool-call index 非整数或为负；
- content、id、name、arguments 碎片不是 text/null。

所有上述情况统一转换为 `ModelResponseError`，不会以 `TypeError`、`ValueError` 等内部异常泄漏，也不会执行可能被截断或错位的工具调用。

### 4. 错误恢复与上下文可见性

- `TimeoutExpired` 的部分输出在某些平台可能是 bytes；现在统一安全解码，避免超时处理自身再次失败。
- 请求发生上下文裁剪时发出 `context_trimmed` 事件，终端展示消息数和字符数前后变化，使隐藏的上下文管理变得可观察。
- `tool_end` 事件携带 metadata，界面无需从自然语言正文猜测路径、退出码或截断状态。

## 测试证据

1.1 新增 7 项测试，完整测试由 60 项增加到 67 项：

- 成功的 inspect 命令不能通过写后验证门；
- 嵌套 array item 与 enum 校验；
- timeout 的 bytes 部分输出；
- 畸形 SSE JSON、index 和碎片类型；
- 纯文本启动页不含 ANSI；
- 写入内容不会被工具事件完整打印。

运行：

```powershell
$env:PYTHONDONTWRITEBYTECODE = "1"
.\.venv\Scripts\python.exe -m unittest discover -s tests -v
```

当前结果：`Ran 67 tests`，`OK`。

### 真实模型回归

2026-09-02 使用固定 `testJARVIS@demo-bug-start` 做了一轮独立 clone 实机回归：

- 修改前：9 项测试，3 项失败；
- 修改后：13 项测试，全部通过；
- Agent：`completed / model_final_answer`；
- 10 个模型轮次、16 次工具调用、43.375 秒；
- `run_command` 4 次，最终 `verification_status=passed`；
- 修改 4 个相关文件，新增 4 项边界测试。

这轮证明真实模型能够使用新的必填 `purpose=inspect|verify` schema 并通过验证门。单次成功不构成统计结论，因此保留原三轮基准作为 1.0 回归证据；1.1 合并前还应根据时间决定是否再做完整三轮。

## 1.2 建议优先级

### P0：真正限制副作用

1. Git worktree 任务隔离：每个任务在独立 worktree 修改，结束后展示 diff，由用户决定合并。
2. OS 级命令隔离：受限容器、受限账户或 Windows Job/Sandbox；网络默认关闭，按任务授权。
3. 修改前后快照与回滚命令：默认不自动回滚，但为用户生成明确、可审阅的恢复点。

这三项比新增更多工具更优先，因为它们直接控制 Coding Agent 的 blast radius。

### P1：提高长任务成功率

1. token-aware context：模型适配层提供精确 token 预算。
2. 可审计 compaction：压缩旧轨迹时保留目标、约束、已修改文件、验证结果和未解决问题，并保存压缩前 checkpoint。
3. 结构化 task ledger：普通模式也能维护 pending/in-progress/verified，而不只依赖对话记忆。
4. patch/diff 工具：支持多处编辑、冲突检测和提交前 diff 展示，保留 `edit_file` 作为小改动安全路径。

### P2：协议与评测

1. provider adapters：分别为 OpenAI Responses、Anthropic 和兼容 Chat Completions 做契约测试。
2. 轨迹记录：稳定 JSONL event log，支持重放、失败分类和成本比较。
3. 扩展固定评测集：覆盖单文件 Bug、多文件功能、配置错误、长输出、恶意仓库指令和验证欺骗。
4. 成功标准从“测试退出 0”扩展为需求 ID、命令、退出码和关键产物的机器可读追踪矩阵。

### 暂缓

- 默认并行写入；
- 无审批的长期记忆与自我改写；
- 多 Agent；
- 消息平台、语音和通用浏览器能力。

理由是这些能力会扩大并发、隐私和错误传播问题。在单 Agent 的隔离、长上下文和评测仍可加强时，先扩大自主性不利于解释和控制。
